This behavior is happening because all guardrails run independently and in parallel for each user turn, and the decision also depends on the conversation context available at that point.

In the first message, the user only shared a number, which did not clearly match a pre-booking travel intent. So the unified guardrail treated it as insufficient/deviated context and asked the user to share flight details or booking reference.

When the user repeated the same number in the next turn, the context had changed because booking reference was already mentioned in the previous response. So the post-booking guardrail interpreted the repeated number as a possible booking/reference number and routed it to the post-booking flow.

So the difference is not because the same input is handled randomly, but because the second turn has additional conversation context, which changes the guardrail interpretation.
