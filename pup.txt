You are working on an existing flight-booking agent implementation.

Goal:
Migrate the existing GPT-4.1 based agent prompt and behavior to a GPT-5.5 compatible agentic implementation, while preserving the current business logic and improving tool usage discipline.

Context:
There is already an existing agent built using a GPT-4.1 style prompt. The main task is to convert that agent to GPT-5.5 and rewrite/refactor the prompt so it follows GPT-5.5 agentic best practices:

- Clear role and task definition
- Clear tool usage rules
- Minimal context loading
- No unnecessary large context inside the initial prompt
- Dynamic tool calls only when required
- Strong grounding on tool results
- No hallucination if tool/context data is unavailable
- Better follow-up handling
- Better reasoning around when to search flights, predict prices, or answer from already generated contracts

Existing Tools:
The agent currently needs to support these tools:

1. Flight Search Tool
   Purpose:
   - Search available flights based on the user query.
   - Use this when the user asks to find, compare, book, or search flights.
   - Example queries:
     - “Find flights from NYC to LAX tomorrow”
     - “Show me cheapest flights to London”
     - “I need a flight from Delhi to Mumbai on Friday”

2. Price Prediction Tool
   Purpose:
   - Predict or estimate whether flight prices may increase/decrease.
   - Use this when the user asks about price trends, whether to book now or wait, or future fare prediction.
   - Example queries:
     - “Should I book now or wait?”
     - “Will this flight price increase?”
     - “Predict price for this route next week”

New Tool Requirement:
Add a third tool:

3. Generated Contracts Context Tool

Suggested name:
`getGeneratedContractsContext`

Purpose:
This tool should return the current generated flight contracts/offers/context that were already created earlier in the conversation/session when Flight Search Tool called .

Important:
Do NOT inject all generated contract context into the initial system prompt or agent prompt.

Reason:
The generated contracts object can become very large, and most user queries do not require it. The agent should fetch this context dynamically only when the user asks something related to the already generated contracts.

The tool should be called only when the user asks follow-up questions about previously generated contracts/offers.

Examples where this tool SHOULD be called:
- “For the third contract, what is the airline?”
- “Which airline is in contract 2?”
- “Compare the first and third contract”
- “Which of these contracts is cheapest?”
- “What is the baggage policy for the selected contract?”
- “Tell me the departure time of the second option”
- “Among the generated contracts, which one is best?”
- “What are the details of contract number 3?”

Examples where this tool should NOT be called:
- User is asking for a completely new flight search
- User has provided a new route/date/passenger requirement
- User is only asking for price prediction without referencing existing contracts
- User is having a generic conversation unrelated to generated contracts

Implementation Expectations:

1. Inspect the current agent implementation
   - Find the existing GPT-4.1 prompt.
   - Find where the current agent is initialized.
   - Find the current Flight Search Tool and Price Prediction Tool implementation.
   - Preserve existing behavior unless changes are required for GPT-5.5 compatibility.

2. Convert the agent to GPT-5.5
   - Update model configuration from GPT-4.1 to GPT-5.5.
   - Refactor the prompt to be GPT-5.5 agent-friendly.
   - Make tool routing explicit.
   - Avoid putting large runtime objects directly into the prompt.
   - Keep instructions clean, structured, and deterministic.

3. Add the new Generated Contracts Context Tool
   - Create a new tool named `getGeneratedContractsContext` or an equivalent clear name.
   - This tool should return the latest generated contracts/offers from the current session/application context.
   - The tool should not mutate anything.
   - The tool should only return the required current context.
   - If no contracts exist, it should return a clear empty-state response like:
     “No generated contracts are currently available.”

4. Update agent tool-routing behavior
   The agent should decide between tools like this:

   - Use Flight Search Tool when user wants to search/find flights.
   - Use Price Prediction Tool when user asks about price trends or whether to book/wait.
   - Use Generated Contracts Context Tool when user asks questions about already generated contracts/options/offers.
   - Use multiple tools only when needed.
   - Do not call tools unnecessarily.

5. Update the prompt with rules like this:

   Agent Role:
   You are a flight-booking assistant that helps users search flights, compare generated flight contracts, and answer questions about pricing and previously generated offers.

   Core Rules:
   - Always understand whether the user is asking for a new flight search, price prediction, or information about already generated contracts.
   - If the user asks about existing/generated contracts, call the Generated Contracts Context Tool before answering.
   - Never assume contract details from memory.
   - Never hallucinate airline, price, timing, baggage, or route details.
   - If contract context is unavailable, politely say that no generated contracts are available and ask the user to search flights first.
   - Do not include the full generated contracts object in the initial prompt.
   - Keep responses concise, useful, and grounded in tool results.

6. Add examples inside the prompt if useful

   Example 1:
   User: “For the third contract, what is the airline?”
   Expected behavior:
   - Call `getGeneratedContractsContext`
   - Read the third contract from returned context
   - Answer with the airline name only, plus any useful minimal detail

   Example 2:
   User: “Find flights from Delhi to Dubai tomorrow”
   Expected behavior:
   - Call Flight Search Tool
   - Do not call Generated Contracts Context Tool

   Example 3:
   User: “Should I book this now or wait?”
   Expected behavior:
   - If “this” refers to an existing generated contract, first call Generated Contracts Context Tool
   - Then call Price Prediction Tool if prediction data is required
   - Answer based on available data

   Example 4:
   User: “Compare contract 1 and contract 3”
   Expected behavior:
   - Call Generated Contracts Context Tool
   - Compare only using returned contract context
   - Mention if either contract number does not exist

7. Add validation and edge cases

   Handle:
   - No generated contracts available
   - User asks for contract number that does not exist
   - User says “this one” or “selected one” but no selected contract is stored
   - Contract context is too large
   - Missing fields in contract data
   - Tool errors
   - Ambiguous user query

8. Testing / Acceptance Criteria

   After implementation, verify:

   - Existing flight search still works.
   - Existing price prediction still works.
   - New contract-related questions call the new context tool.
   - Initial agent prompt does not contain the large generated contracts object.
   - Agent does not answer contract-specific questions without fetching current context.
   - Agent gives a safe fallback if no contracts exist.
   - Agent correctly handles contract indexes like first, second, third, contract 1, contract 2, etc.
   - Agent does not call the contract context tool for fresh flight searches.
   - Agent behavior is compatible with GPT-5.5.

  - No contracts available case

Keep the implementation clean, modular, and easy to extend.
