Task:
Update the Digital API flight search service workflow to use UID from context instead of calling the default settings API.

Context:
Currently the service uses 3 APIs:
1. `/default-setting/get` - used to generate/fetch cookies like `UID`
2. `/validate-search` - used to validate/initiate search and generate `SID`
3. `/listing` - used with `SID` to start polling and fetch flight contracts

Now `/default-setting/get` should be removed from this workflow.

New Requirement:
The calling service will already provide `UID` in the request/context.
We must use this incoming `UID` directly for:
- `/validate-search`
- `/listing`
- `/apply-filter`

Required Workflow:
1. Read `UID` from request/context.
2. Do not call `/default-setting/get`.
3. Call `/validate-search` using:
   - user search payload
   - incoming `UID`
4. Use the generated `SID` from `/validate-search`.
5. Call `/listing` using:
   - `SID`
   - same `UID`
6. Start polling `/listing` and collect flight contracts.
7. Store/use the contract state returned from listing, especially `CNT` key.
8. For further user filters, call `/apply-filter`.

Apply Filter Rules:
- `/apply-filter` must always receive the same `UID`.
- `UID` is important because it maintains current search/filter state.
- Each filter must be applied separately.
- Do not send multiple filter types in one `/apply-filter` call.
- Example:
  - baggage filter → one `/apply-filter` call
  - layover airport filter → another `/apply-filter` call
  - duration filter → another `/apply-filter` call
- When a new filter is applied, previous filters should remain active because state is tracked by `UID`.

Supported Filters:
Use the existing reference code/context file to understand current `/apply-filter` implementations.
The reference code may only contain 2-3 filters for now.
First implement the workflow correctly for those existing filters.

Examples of future filters:
- stops
- flight timings
- departure/arrival airport
- layover airport
- baggage
- total duration
- layover duration

Important:
- Keep `UID` consistent across validate search, listing, polling, and apply filter.
- Remove dependency on `/default-setting/get`.
- Do not regenerate UID anywhere.
- Do not break existing listing polling behavior.
- Reuse existing apply-filter reference code and integrate it into the current Digital API service cleanly.

Acceptance Criteria:
- `/default-setting/get` is no longer called.
- `UID` is read from context/request.
- `/validate-search` works with incoming `UID`.
- `/listing` works with same `UID` and generated `SID`.
- Polling still returns flight contracts correctly.
- `/apply-filter` works using same `UID`.
- Multiple filters are applied through multiple sequential `/apply-filter` calls.
- Existing 2-3 reference filters are implemented and tested.
