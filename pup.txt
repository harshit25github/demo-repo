### 2. Investigate the Main Problem

**Example:**

User searches for flights from New York → Delhi, India.

The Flight Agent correctly identifies Delhi, India.

Later, the user requests:

"Find me hotels in Delhi."

However, the Hotel IntelliSuggest API returns multiple locations:

- Delhi, India
- Delhi, New York, USA
- Delhi, Ontario, Canada
- Other similarly named locations

If the Hotel Agent blindly selects the first result, it may search for hotels in the wrong country.

**Expected intelligence:** The Hotel Agent should recognize the flight destination and intelligently resolve Delhi, India, instead of blindly trusting the first location suggestion.

Investigate why our current system can fail in these situations.

### 3. Identify All Possible Corner Cases

Think beyond this example and identify comprehensive real-world scenarios, including:

- Same city name across multiple countries or states.
- User's current coordinates biasing destination searches.
- Flight destination and hotel destination matching.
- Flight destination and hotel destination intentionally differing.
- Nearby cities, airports, landmarks, and tourist destinations.
- Multi-city flight itineraries with multiple hotel destinations.
- Round-trip and connecting-flight locations.
- User changing the destination during a conversation.
- Missing, partial, outdated, or conflicting Flight Context.
- Hotel searches without any previous flight search.
- Ambiguous location types: cities, hotels, POIs, airports, regions.
- Multiple matching hotel location codes.
- Incorrect country/state inference.
- Conflicting user messages and hydrated context.
- Cases where the destination is not directly served by an airport.

Also identify additional corner cases discovered through the actual codebase and API responses.

### 4. Explore Existing APIs and Context for Better Intelligence

We already have substantial location information in our system. Investigate how to leverage it.

**A. Flight Agent Location Resolution**

- What metadata does the Flight Location API provide?
- Does it expose city, state, country, airport codes, or coordinates?
- Can we reuse its resolved destination information for Hotel Agent?
- How reliably can the hotel destination be mapped to the flight destination?

**B. Digital Flight Search API**

Inspect actual flight search responses and contracts.

Determine whether we can extract:

- Destination city.
- Destination state.
- Destination country.
- Airport IATA code.
- Latitude/longitude or other geographic identifiers.

Verify what is actually available in the API response instead of assuming these fields exist.

Also investigate whether existing `searchCriteria` or Flight Context already contains this information, so we can avoid unnecessary API calls.

**C. Hotel Location APIs**

Investigate both available Hotel Location Search APIs.

Determine:

- Can we filter locations by country or state?
- Can we use coordinates as a destination hint rather than the user's current location?
- Can we reliably distinguish between cities, hotels, POIs, and regions?
- How are location codes assigned and resolved?
- Can we select the correct code using existing context and returned location metadata?
- Which API is more reliable for ambiguous location resolution?

Use actual API contracts and test responses to validate your findings.

**Flight Agent + Hotel Agent + Trip Planner**

Expected: Hotel Agent should use the already-resolved Delhi, India destination.

However:

User: "Find hotels in Agra instead."
