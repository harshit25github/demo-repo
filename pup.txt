# Gateway vs. Manager Architecture

**Project:** Multi-Agent Travel Assistant  
**Purpose:** Architecture comparison and recommendation for management  
**Date:** 10 November 2026

## Executive Summary

**[Likely] Recommendation:** Adopt the **Manager architecture** as the primary orchestration pattern for our travel assistant. Gateway is suitable for straightforward intent-based handoffs, but our system increasingly needs context-aware decisions, coordination across specialist agents, and consistent user-facing responses.

**Important qualification:** Changing the architecture alone will **not** resolve inaccurate guardrail classifications, missing context, or tool errors. The benefits depend on reliable context propagation and specialist feedback, and must be verified with comparative tests.

## 1. Gateway vs. Manager — Comparison

| Area | Gateway Architecture | Manager Architecture |
|---|---|---|
| **Main responsibility** | Classifies intent and hands control to a specialist. | Orchestrates specialist agents and owns the final response. |
| **Routing** | Primarily makes an upfront routing decision. | Can select specialists based on conversation history, application state, and intermediate results. |
| **Ambiguous requests** | More dependent on the initial classifier and routing prompt. | Can evaluate conflicting signals and ask for clarification when evidence is insufficient. |
| **Conversation context** | Handoffs can pass history to the specialist; consistency depends on the implementation. | Manager has a central view, but must explicitly pass relevant context to agents invoked as tools. |
| **Multiple specialist needs** | Usually optimized for handing a turn to one specialist. | Can combine Flight, Trip Planner, Policy, and Pages agent contributions within one turn. |
| **Response consistency** | Different specialists may have different response styles. | One response owner can maintain a consistent tone and presentation. |
| **Error recovery** | Often depends on the specialist that received the handoff. | Can interpret specialist failure feedback and decide whether to clarify, retry safely, or provide a partial answer. |
| **Cost and latency** | Often simpler and faster for straightforward single-agent requests. | May increase latency and token usage because of extra orchestration/model calls. |
| **Complexity** | Simpler for narrow, clearly classified tasks. | More flexible for cross-domain tasks, but needs disciplined context and tool contracts. |

## 2. How Manager Would Work in Our System

```text
User request
   |
   v
Input safety checks + pre-/post-booking classification signals
   |
   v
Manager Agent
   |  Reads conversation history and current application context
   |  Determines user intent and whether clarification is required
   |
   +--> Flight Agent        (new search, filters, price prediction)
   +--> Trip Planner Agent  (destination ideas, itinerary changes)
   +--> Policy Agent        (airline rules and policy questions)
   +--> Pages Agent         (page-specific tasks/navigation)
   |
   v
Specialists return findings, actions, missing fields, and failures
   |
   v
Manager evaluates results and composes one user-facing response
   |
   v
Application delivers response and relevant updated context/cards
```

**[Certain, based on our design discussions]** We use OpenAI conversation sessions and application-provided context. For flight workflows, `searchCriteria` is intended to be the canonical search state rather than a separate duplicated flight-search context.

**[Likely]** Manager should own routing, orchestration, and the final answer; individual specialists should own their domain logic. For example, the Flight Agent determines whether to call `flight_search`, `apply_filter`, or `price_prediction`, while Manager makes sure the correct domain was engaged and communicates the verified outcome.

## 3. Why Manager Is Better for Our Use Case

### A. More reliable ambiguity handling

Our users may say: **"Can I change my seat?"** This can mean choosing a seat before booking or modifying an existing booking.

- **Gateway:** A lightweight classifier may send the request directly down a pre-booking or post-booking path based on incomplete evidence.
- **Manager:** Can consider the current page, active flight search, conversation history, verified booking evidence, and classifier output before taking the next step.

**[Likely] Benefit:** Fewer avoidable routing mistakes, *if* the needed context is available and accurate. When evidence remains insufficient, the system should ask a focused clarification instead of assuming a booking exists.

### B. Better cross-agent coordination

A request such as **"Find flights to Dubai next week and tell me the cabin baggage policy"** spans both flight search and airline policy.

**[Likely] Benefit:** Manager can coordinate the two specialists and combine their verified findings into one answer rather than forcing the entire request through one specialist.

### C. More consistent responses

Specialists can return structured, factual feedback instead of independently writing the final user response.

**[Likely] Benefit:** A single final response owner can consistently acknowledge the user's request, accurately report completed actions, distinguish facts from limitations, and present useful next steps.

### D. Better handling of failures and partial completion

If `flight_search` fails, or a filter cannot be applied, the specialist should return the outcome and reason to Manager.

**[Likely] Benefit:** Manager can explain what succeeded and what failed, or decide whether clarification or a safe retry is appropriate. It must not invent tool successes or booking/search results.

### E. Easier evolution as we add specialists

**[Likely] Benefit:** New domain capabilities can be introduced as specialist agents without requiring every existing agent to manage every other agent's conversation and response behavior.

## 4. What Manager Does *Not* Automatically Fix

1. **Guardrail/classifier inconsistency.** A wrong pre-/post-booking classification remains a risk; Manager can use the result as evidence, but it is not automatically a correct replacement classifier.
2. **Missing or stale context.** If booking evidence, page state, session history, or `searchCriteria` is absent or incorrect, Manager can still route incorrectly.
3. **Incomplete specialist feedback.** If a specialist omits an error, limitation, or context update, the final answer may still be misleading.
4. **Safety and authorization.** Hard guardrails and deterministic authorization checks must remain enforced independently; Manager should not override them.
5. **Latency and cost.** Additional orchestration calls may increase time and token consumption.

**[Certain, from prior internal review]** Earlier Manager-mode testing identified examples of routing misses, stale suggested questions, and itinerary edits that did not fully explain what changed. This shows that Manager is not a guarantee of correctness; integration quality still matters.

## 5. Recommended Operating Rules

- **Keep hard safety/authorization boundaries outside model discretion.** Use guardrails for blocking prohibited actions; use application checks for permissions and irreversible operations.
- **Treat ambiguous intent predictions as signals, not unconditional truth.** Combine them with verified user/booking/page context. Do not interpret an uncalibrated model-generated percentage as an actual probability of correctness.
- **Use one authoritative state per workflow.** For flight search, rely on canonical `searchCriteria`, including the required search fields and updated filters.
- **Make specialist feedback actionable.** Each specialist should provide what it attempted, what completed, relevant facts, missing inputs, and limitations/failures.
- **Keep domain logic within specialists.** Manager should not duplicate flight-tool selection rules, policy retrieval, or other specialist implementation details.
- **Ask clarifying questions only when necessary.** If context already answers the ambiguity, proceed; otherwise ask the minimum question needed.

## 6. How We Should Validate the Improvement

**[Certain]** Architectural superiority has not yet been demonstrated with an apples-to-apples benchmark in our discussions. Compare Gateway and Manager against the **same labeled multi-turn conversations**.

| Metric | What to check |
|---|---|
| **Routing accuracy** | Was the correct specialist selected? |
| **Pre-/post-booking error rate** | Did the system incorrectly classify a booking-related request? |
| **Context retention** | Did it preserve dates, passengers, airline preferences, search state, and prior user decisions? |
| **Ambiguity resolution** | Did it infer only what the evidence supported, or ask an appropriate clarification? |
| **Tool correctness** | Were search vs. filter operations and their inputs correct? |
| **Response quality** | Was the final answer consistent, accurate, and transparent about partial failures? |
| **Operational efficiency** | What were the latency, token cost, and failure/retry rates? |

## Final Recommendation for Management

**[Likely]** We should prefer **Manager** as the orchestration layer for our multi-agent travel assistant because it is better aligned with our actual workload: complex multi-turn requests, pre-/post-booking ambiguity, coordination across specialists, and the need for a unified user experience.

Gateway remains an efficient option for straightforward requests with clear intent. Manager's advantage is **centralized control over the conversation and final response**, not inherently smarter classification.

**The next priority is to validate that our Manager receives complete and accurate context, that classifiers provide evidence-based signals, and that specialists return dependable feedback.** We should then measure the improvement against Gateway before making quantitative reliability claims.
