Debug and fix stale `segments` issue in Flight Agent searchCriteria update flow.

Problem:
After Flight Agent flow completes, we update final `searchCriteria` from the latest context and send it back as a chunk.

Most fields are updating correctly, but `searchCriteria.segments` sometimes remains stale.

Likely scenario:
- Existing `searchCriteria` comes in request.
- It is hydrated as base flight context.
- User changes route/date/trip options.
- Flight Agent updates context and runs flight search.
- Final `searchCriteria` gets updated, but `segments` still contain old route/date values.

Possible issue area:
This may be happening in the flight search flow where segments are created/updated after `flight_search_tool` runs.

Please debug both areas:

1. Context → searchCriteria mapper
- Check where final `searchCriteria` is generated after stream ends.
- Verify `segments` are mapped from latest flight context, not old request searchCriteria.

2. Flight search flow
- Check how `segments` are created/updated during `flight_search_tool`.
- Verify updated origin/destination/date/tripType are reflected in context segments.
- Ensure old hydrated segments are not reused after user changes route/options.

Add focused logs:
- incoming `searchCriteria.segments`
- base flight context after hydration
- user-requested changes
- flight context before `flight_search_tool`
- flight context after `flight_search_tool`
- final generated `searchCriteria.segments`
- final streamed searchCriteria chunk

Expected behavior:
- If user changes origin/destination/date/trip type, final `segments` must reflect latest values.
- Old request/DB segments should not overwrite updated context.
- One-way, round-trip, and multi-city segments should be verified.

Deliverable:
- Find where stale segments are introduced.
- Fix segment update logic.
- Add tests for route/date changes with existing searchCriteria.
- Share before/after payload examples and logs.
