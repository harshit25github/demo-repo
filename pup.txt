Plan Flight Agent dynamic prompt context fallback for route/date fields.

Do not implement yet. First inspect the code and propose the cleanest enhancement plan.

## Problem

Flight Agent dynamic prompt currently receives both:
- `summary` context
- `flight` context

Both may contain similar information:
- departure/origin location
- arrival/destination location
- outbound date
- return/inbound date
- passenger info

Sometimes `flight` context has empty values, but `summary` context has valid values.  
Because both objects are injected separately, the agent can get confused and ask for departure/arrival/date again even when the information exists in summary.

## Goal

Create one normalized dynamic prompt object for Flight Agent that resolves the best available values before injecting into the prompt.

Priority:

```txt
flight context > summary context
````

But fallback only when flight value is truly empty.

## Required fallback logic

### Location fields

Flight context examples:

```ts
flight.resolvedOrigin = {
  userCity: "",
  airportIATA: ""
}

flight.resolvedDestination = {
  userCity: "",
  airportIATA: ""
}
```

Summary context examples:

```ts
summary.origin = {
  city: "",
  iata: ""
}

summary.destination = {
  city: "",
  iata: ""
}
```

Rules:

1. For departure location:

* First check `flight.resolvedOrigin`.
* If either `userCity` or `airportIATA` has a non-empty value, use flight origin.
* Only if both are empty/null/missing, fallback to `summary.origin`.

2. For arrival location:

* First check `flight.resolvedDestination`.
* If either `userCity` or `airportIATA` has a non-empty value, use flight destination.
* Only if both are empty/null/missing, fallback to `summary.destination`.

3. Do not merge flight + summary partials.

* If flight has any valid origin field, use flight origin as source.
* If flight is fully empty, then use summary origin.
* Same for destination.

### Date fields

Apply same priority for:

* outbound date
* return/inbound date

Rules:

* Use flight date if present.
* If flight date is empty/null/missing, fallback to summary date.
* Do not overwrite actual flight context.
* This fallback is only for dynamic prompt hydration unless plan recommends otherwise.

## Expected design

Create a compact resolved object like:

```ts
resolvedFlightPromptContext = {
  departureLocation: {
    city: "",
    iata: "",
    source: "flight" | "summary" | "missing"
  },
  arrivalLocation: {
    city: "",
    iata: "",
    source: "flight" | "summary" | "missing"
  },
  outboundDate: {
    value: "",
    source: "flight" | "summary" | "missing"
  },
  returnDate: {
    value: "",
    source: "flight" | "summary" | "missing"
  },
  passengers: {},
  tripType: "",
  cabinClass: ""
}
```

Use this resolved object in the dynamic prompt so the agent does not hallucinate missing fields.

## Important rules

* Do not change stored `flight` context schema.
* Do not change stored `summary` context schema.
* Do not mutate context during fallback.
* Do not overwrite flight values with summary values.
* This should be prompt-hydration fallback only.
* Keep implementation simple and readable.
* Avoid over-engineering and unnecessary fallback chains.
* Add source labels for debugging only if useful.

## Tests to plan

Create test cases for:

1. Flight origin/destination present → use flight values.
2. Flight origin empty, summary origin present → use summary origin.
3. Flight destination empty, summary destination present → use summary destination.
4. Flight has only IATA, summary has city + IATA → still use flight.
5. Flight has only city, summary has IATA → still use flight.
6. Both flight and summary missing → mark missing.
7. Flight outbound date missing, summary outbound date present → use summary date.
8. Flight date present, summary has different date → use flight date.
9. Agent should not ask for arrival location if fallback resolved it from summary.
