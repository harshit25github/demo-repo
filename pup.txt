Thoroughly investigate and fix our **Post-Booking Decision API Guardrail**, focusing on authentication context, intent classification, and incorrect pre-booking request blocking.

### 1. Fix `hasUpcomingTrips` Context Handling

Currently, we are passing `hasUpcomingTrips` even when the user is not logged in.

- Trace how authentication state and `hasUpcomingTrips` are generated, hydrated, and passed into the Decision API.
- For unauthenticated users, **do not pass `hasUpcomingTrips`**. Its value is unknown, not `false`.
- Only provide this identifier when the user is authenticated and we have reliable information.
- Ensure missing authentication context doesn't cause incorrect assumptions about booking ownership.
- Preserve the distinction between **intent classification** and **whether the user can actually manage a booking**.

### 2. Fix Incorrect Post-Booking Classification

We have observed a serious issue:

**User:** "Make a new booking."

**Current incorrect behavior:** The Decision API classifies this as post-booking and blocks the request, even when the new-booking intent has a higher probability.

**Expected behavior:** Route it through the normal **pre-booking flow**.

The guardrail must intelligently distinguish:

| User intent | Expected classification |
|---|---|
| "Make a new booking" | Pre-booking |
| "Book a flight to London" | Pre-booking |
| "Find me another flight" | Pre-booking, unless context indicates an existing-booking change |
| "Change my existing booking" | Post-booking |
| "Cancel my reservation" | Post-booking when referring to an existing reservation |
| "Check my booking status" | Post-booking |
| "I need help with my previous booking" | Post-booking |
| "I want to book again" | Pre-booking, unless the context indicates an existing-booking action |

**Critical:** Explicit new-booking intent must never be overridden merely because the message contains the word "booking."

### 3. Improve Decision API Intelligence

- Thoroughly inspect the existing Decision API policy, classification descriptions, probability/confidence handling, context hydration, and final routing logic.
- Identify why the higher-probability `new_booking` classification is being ignored.
- Check whether confidence interpretation, output mapping, or downstream guardrail logic is reversing the Decision API's actual decision.
- Improve semantic understanding of new-booking vs. existing-booking intent.
- Use conversation history appropriately to resolve short or ambiguous follow-ups.
- Do not rely on keyword matching or simplistic authentication rules.

**Important distinction:**

Authentication status and `hasUpcomingTrips` must not independently determine whether a request is pre-booking or post-booking.

An unauthenticated user can still ask about an existing booking. Such intent belongs to post-booking classification, even if completing the action requires authentication later.

### 4. Comprehensive Regression Testing

Test the actual Decision API and end-to-end routing across:

- Logged-in and logged-out users.
- Explicit new-booking requests.

Specifically verify:

- Selected classification and why it was selected.
