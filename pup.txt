Enhance `generate_contracts_context` fallback handling when current flight results are missing.

Scenario:
- User may enter chatbot from listing page after a flight search was already done outside the Flight Agent.
- In that case, `flightContext` may already contain search criteria/searchKey/route/date/passenger/cabin details, but `flight.searchResults` or contracts array may be empty because Flight Agent did not initiate the original search.
- If user asks something like:
  - "Which is the cheapest option?"
  - "Compare the current contracts"
  - "Which flight is best among these?"
  then `generate_contracts_context` needs actual flight contracts/results to reason on.

Required fix:
- Inside `generate_contracts_context`, check if current flight results/contracts are empty.
- If results exist, use them directly. Do not trigger a new search.
- If results are empty, use the existing `flight` context search criteria to fetch/generate flight results first.
- Reuse/extract the same digital service search-call logic currently used inside `flight_search_tool`.
- Support all trip types correctly:
  - one-way
  - round-trip
  - multi-city
- After fetching results:
  - update `flight.searchResults/contracts`
  - update latest `searchKey` and context in the flight same flight_search tool
  - then generate contracts context normally for agent reasoning.

Important:
- Do not call digital search if contracts/results are already available.
- Do not hallucinate cheapest/best flight if results are empty and search cannot be fetched.
- If required search criteria is missing, return safe feedback instead of failing.
- Ensure multi-city payload format matches the same format used by `flight_search_tool`.

Test cases:
1. Existing contracts available → `generate_contracts_context` uses existing results, no digital API call.
2. Empty contracts + valid one-way context → fetch results, update context, generate contract context.
3. Empty contracts + valid round-trip context → fetch results correctly.
4. Empty contracts + valid multi-city context → fetch results with correct segment format.
5. Empty contracts + missing required criteria → return safe feedback.
6. User asks "cheapest flight among current options" after listing-page entry → fetch results first, then answer using actual contracts.
7. Verify latest `searchKey` is preserved/updated after fallback search.
8. Verify no duplicate search call happens if results already exist.

Deliverable:
- Implement the fallback.
- Provide a short report with:
  - when fallback search triggers
  - payload used for one-way/round-trip/multi-city
  - context fields updated
  - test results
