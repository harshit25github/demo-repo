Task: Enhance the Flight Search Tool to use sensible defaults instead of asking unnecessary follow-up questions.

Current behavior:
The flight search agent asks the user for all required flight details before searching:
- origin
- destination
- travel date
- return date
- trip type
- passengers
- cabin class

Required enhancement:
The agent should ask only for truly missing blocking information.
For non-critical fields, it should assume sensible defaults and continue with the flight search.

Core rule:
Do not block the flight search just because optional details are missing.

Blocking details:
The agent must ask the user only if these are missing:
- origin
- destination
- departure date

Default assumptions:
If the user does not provide these fields, assume:

{
  "trip_type": "one_way",
  "passengers": {
    "adults": 1,
    "children": 0,
    "infants": 0
  },
  "cabin_class": "economy"
}

Round trip handling:
- If the user provides a return date, treat it as a round trip.
- If the user explicitly says “round trip” but does not provide a return date, ask only for the return date.
- If no return date is provided and the user does not mention round trip, assume one-way.

Passenger handling:
- If passenger count is missing, assume 1 adult.
- If the user says “we”, “family”, “kids”, or gives unclear passenger info, ask for passenger count only if required for accurate pricing.
- Otherwise default to 1 adult.

Cabin class handling:
- If cabin class is missing, assume economy.
- Only use premium economy/business/first if explicitly mentioned by the user.

Multi-city handling:
- Only use multi-city if the user explicitly asks for it.
- Do not assume multi-city from vague wording.
- If multi-city is requested but segment details are incomplete, ask for the missing segment details.

Agent behavior:
- Do not ask a long form with all fields.
- Ask only the minimum missing information.
- If defaults are used, mention them briefly in the response.
- Example:
  “I’ll search one-way economy flights for 1 adult.”

Tool behavior:
- The Flight Search Tool should accept default values when optional fields are missing.
- The tool should normalize the final search request before execution.
- The final normalized request should always include:
  - origin
  - destination
  - departure_date
  - trip_type
  - passengers
  - cabin_class
  - return_date, only if round trip
  - segments, only if multi-city

Expected normalized examples:

Example 1:
User: “Find flights from Delhi to Dubai on 20 June”

Normalized request:
{
  "origin": "Delhi",
  "destination": "Dubai",
  "departure_date": "2026-06-20",
  "trip_type": "one_way",
  "passengers": {
    "adults": 1,
    "children": 0,
    "infants": 0
  },
  "cabin_class": "economy"
}

Example 2:
User: “Find round trip flights from Mumbai to London on 10 July”

Agent should ask:
“What is your return date?”

Example 3:
User: “Find business class flights from Bangalore to Singapore tomorrow for 2 people”

Normalized request:
{
  "origin": "Bangalore",
  "destination": "Singapore",
  "departure_date": "<resolved tomorrow date>",
  "trip_type": "one_way",
  "passengers": {
    "adults": 2,
    "children": 0,
    "infants": 0
  },
  "cabin_class": "business"
}

Validation:
Add tests to verify:
- missing cabin class defaults to economy
- missing passenger count defaults to 1 adult
- missing trip type defaults to one-way
- round trip without return date asks only for return date
- flight search does not ask unnecessary questions
- normalized search request is complete before calling the flight API

Expected output:
After implementation, explain:
1. What default assumptions were added
2. What fields still require user clarification
3. How the normalized request is built
4. What tests were added
