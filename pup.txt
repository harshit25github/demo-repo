We need to investigate and optimize **Manager V2's streaming response and image/icon hydration flow** for production.

### Current Problem

- The Manager streams text chunks to the client.
- After text streaming finishes, the Summary Extractor runs for approximately 5–8 seconds.
- Only then does the final `status: "done"` chunk arrive with the complete response and hydration metadata.
- As a result, users read the unhydrated text first, and images/icons appear several seconds later.

This creates a poor user experience.

### Explore These Solutions in Priority Order

**Option 1 — Remove the Summary Extractor (Highest Priority)**

Investigate whether Trip Planner V2 or the Manager can generate the required summary schema and image/icon metadata during their existing execution.

- Can we eliminate the separate Summary Extractor LLM call for Manager V2?
- Can existing specialist output provide everything needed for the final response?
- What about Flight-only, Trip-only, combined-agent, and general conversation scenarios?
- Can we preserve all existing summary fields, context updates, and client contracts?

If feasible, this is our preferred solution.

**Option 2 — Progressive Hydration**

If removing the extractor is not feasible, investigate whether we can hydrate location images/icons progressively as text chunks stream.

Determine whether this can work reliably with partial Markdown, location references, and our existing Inventory API.

**Option 3 — Immediate Complete-Response Hydration**

If progressive hydration is impractical, investigate sending a complete, hydration-ready response chunk immediately after the Manager finishes generating text, without waiting for the Summary Extractor.

The client should be able to replace/update the streamed content with hydrated content without visible flickering or duplication.

Keep the final `done` event and response lifecycle consistent.

### R&D Requirements

1. Trace the complete Manager streaming → Summary Extractor → image/icon hydration → `done` flow.
2. Identify exactly why hydration depends on the Summary Extractor.
3. Inspect existing schemas, state updates, streaming events, and Inventory API integration.
4. Compare all three options for latency, reliability, complexity, and compatibility.
5. Recommend the simplest solution that genuinely removes the visible hydration delay.
6. Explain the required changes with exact file references and a step-by-step implementation plan.

### Important

- **Manager V2 only. Do not modify Gateway V1.**
- Preserve streaming behavior and existing API contracts.
- Avoid additional LLM calls and unnecessary wrappers.
- Do not sacrifice response correctness or context persistence for performance.
