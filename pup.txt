Update the **Flight Agent in both Gateway V1 and Manager V2** to handle missing trip types and ambiguous destinations correctly.

### 1. Location Ambiguity
- Ask for clarification whenever a destination has multiple plausible matches.
- Examples:
  - "Delhi to Kochi" → Kochi, India or Kōchi, Japan.
  - "Pragway" → Could mean Prague, Czech Republic, or Paraguay, South America.
- Use conversation context when reliable. Never assume a destination when genuine ambiguity remains.

### 2. Trip Type — Three-Level Validation

**A. Agent Prompt**
- Remove the default `one-way` assumption.
- If trip type is missing, ask the user whether they want one-way, round-trip, or multi-city.
- Do not call `flight_search` until the trip type is confirmed.

**B. Flight Search Tool**
- Add server-side validation for missing or invalid trip types.
- If the Agent accidentally calls `flight_search` without a valid trip type, return clear, actionable feedback instructing it to ask the user.
- Reject the request before executing the search. Never silently default to one-way.

**C. Initial Context / Skeleton**
- Inspect context initialization, search criteria, schemas, and default-value assignments.
- Remove any hardcoded `one-way` defaults.
- Keep trip type unset until explicitly provided or reliably established from conversation context.

### 3. Verification
- Apply consistently across both Gateway and Manager flows.
- Test missing trip types, ambiguous locations, spelling mistakes, tool validation feedback, and multi-turn clarifications.
- Ensure previously confirmed trip types remain preserved.

**Goal:** Enforce these rules at both the **prompt and tool levels**, while removing conflicting defaults from context initialization.

Keep changes minimal and preserve existing functionality.
