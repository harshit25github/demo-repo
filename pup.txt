## Required date context

Add a separate date state like:

```ts
context.flightDate = {
  clock: {
    localDate: string,
    localDateTime: string,
    timeZone: string
  },
  dateIntent?: {
    status: "RESOLVED" | "NEEDS_RETURN_TIMING" | "OUTSIDE_SEARCH_WINDOW" | "INVALID_INTENT",
    kind: "exact" | "weekday" | "week" | "weekend" | "month" | "range" | "flexible",
    range: { startDate: string, endDate: string } | null,
    searchDate: string | null,
    returnDate: string | null,
    priceFallbackDate: string | null,
    timeZone: string,
    resolvedFromDate: string,
    assumptionLabel: string,
    state: "pending" | "used" | "stale" | "invalid",
    stale: boolean,
    usedAtRequestId?: string | null
  },
  routing: {
    pricePredictionStatus: string | null,
    priceFallbackDate: string | null,
    fallbackSearchAttempted: boolean
  }
}
````

## Date lifecycle rules

* Regenerate `clock` on every request using current local date/time and real user timezone.
* Reset `routing` on every request.
* Preserve `dateIntent` across unrelated turns.
* Do not create `dateIntent` on an empty first turn.
* If exact outbound date already exists but `dateIntent` is missing, hydrate an exact used intent.
* Explicit new date intent replaces previous intent.
* Route/passenger/cabin/filter changes should preserve existing date intent.
* Mark date intent stale if `searchDate` is before current local date.
* One-way change may clear old return date.
* Do not hardcode one timezone for all users.

For streaming, persist context only after stream completion.

## Resolver tool

Create/register a tool named:

```txt
resolve_flight_date
```

Input schema:

```ts
{
  kind: "exact" | "weekday" | "week" | "weekend" | "month" | "range" | "flexible",
  relation: "this" | "next" | null,
  offset: number | null,
  weekday: "sunday" | "monday" | "tuesday" | "wednesday" | "thursday" | "friday" | "saturday" | null,
  month: number | null,
  year: number | null,
  exactDate: string | null,
  rangeStart: string | null,
  rangeEnd: string | null,
  tripDurationDays: number | null
}
```

Rules:

* Agent interprets natural language and sends structured payload.
* Tool must not parse raw user text.
* Tool uses `context.flightDate.clock`.
* Tool may use existing flight search context for trip duration/return date.
* Tool updates `context.flightDate.dateIntent`.
* Tool returns resolved date feedback to the agent.

## Date resolution policy

Implement these behaviors:

* `next week` → next Monday to Sunday; search Monday.
* `this weekend` → nearest upcoming Saturday/Sunday; search Saturday.
* `next weekend` → following Saturday/Sunday; search Saturday.
* `next month` → full next calendar month; search first day.
* named month → next valid occurrence; clip past dates.
* weekday → resolve from current local date.
* explicit range → preserve range; search range start.
* flexible → today through today + 89 days.
* flight search booking limit → 359 days.
* price prediction limit → 89 days.
* return date → `searchDate + tripDurationDays`.
* reuse existing outbound-return duration when available.
* round trip without return timing/duration → return `NEEDS_RETURN_TIMING`.

## Flight search integration

* Agent should create the existing structured `flight_search` payload.
* Use `dateIntent.searchDate` as outbound date.
* Use `dateIntent.returnDate` as return date when available.
* After successful search:

  * update active flight search context
  * mark matching date intent as `used`
* If search uses a predicted best date, store it as a new exact used intent.
* Do not ask exact date again if a non-stale `dateIntent.searchDate` exists.
* User response should clearly mention inferred date/assumption naturally.

## Price prediction integration

Use price prediction only for explicit price-intelligence intent:

* cheapest date
* best fare date
* lowest fare
* compare dates
* flexible-price advice
* prediction requests

Normal vague search should follow:

```txt
resolve_flight_date → flight_search
```

Price-intelligence flow should follow:

```txt
resolve_flight_date → price_prediction_tool
```

Implement a temporary adapter that builds price prediction input from `dateIntent`.

Rules:

* Query full today-to-89-day prediction window.
* Also preserve requested/effective user range.
* Filter returned predictions to requested month/range after the tool result.
* Store result in `context.flight.lastPricePrediction`.
* Store only routing status/fallback info in `context.flightDate.routing`.
* Never expose `NO_PREDICTIONS`, unsupported route, internal errors, or raw tool messages to user.
* If usable search date exists and normal-search continuation applies, call `flight_search` once.
* Use `fallbackSearchAttempted` to prevent loops.
* Predicted date becomes durable only after actual flight search.
