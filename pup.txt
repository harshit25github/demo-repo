You are working on a Node.js + Express baggage-retrieval service that uses:
- OpenAI Agents SDK for chat/tool calling
- Qdrant for vector retrieval
- CheapOair baggage directory rows as structured baggage anchors
- airline policy pages as linked policy evidence

Current retrieval code is mainly in:
- src/retrieval/service.js
- src/retrieval/helpers.js
- src/retrieval/query-routing.js

Supporting indexing/vector files:
- src/indexing/hybrid-documents.js
- src/indexing/vector-documents.js
- src/indexing/qdrant-service.js

Evaluation artifacts:
- data/evals/baggage-query-20-latest/report.md
- data/evals/baggage-query-20-url-kb/report.md
- data/evals/baggage-query-20-compare-latest/summary.md

Context:
- We ran 20 baggage-query scenarios against two collections:
  - url_kb_crawlfix
  - url_kb
- Both answered all 20 cases.
- But quality is still not good enough:
  - url_kb_crawlfix: 6 strong, 14 partial
  - url_kb: 4 strong, 16 partial

I need you to analyze and improve the retrieval quality, especially for baggage-policy queries.

Main problems currently observed:

1. Directory row is found, but linked policy detail is still incomplete.
Example:
- Query: "I have a flight from NYC to LAX on JetBlue in economy class, What will be the baggage policy"
- Current issue:
  - route row is found correctly
  - carry-on info is better now
  - checked-bag fee/allowance is still not grounded clearly
  - answer remains partial

2. Same airline page URL is reused for multiple facets.
Example:
- JetBlue firstBagUrl, secondBagUrl, and additionalPolicyUrl all point to the same baggage page
- Current issue:
  - even after facet-first retrieval, the system can still return generic or less useful sections
  - it is hard to reliably isolate exact checked-bag facts from a single hub page

3. Some answers still rely on generic baggage pages instead of exact route/cabin-specific facts.
Examples:
- Turkish JFK -> IST economy
- Turkish IST -> DEL business
- Air France JFK -> CDG economy
- British Airways JFK -> LHR economy
- Qatar JFK -> DOH economy
- Current issue:
  - route row is found
  - policy page is linked
  - but exact checked-bag allowance or class-specific detail is still missing or too generic

4. Fare-brand sensitivity is weak.
Example:
- Query: "I have a flight from ATL to SEA on Delta Air Lines in economy class with basic economy brand, What will be the baggage policy"
- Current issue:
  - the system recognizes the airline and route
  - but brand/fare nuance like Basic Economy is not strongly grounded from retrieved evidence

5. Some airlines still return only row-level evidence with weak official expansion.
Examples:
- Aer Lingus JFK -> DUB business
- Aer Lingus DUB -> BOS economy
- Current issue:
  - directory row is present
  - official airline page expansion is weak or blocked/quarantined
  - result stays partial

6. Retrieval is better in url_kb_crawlfix, but still not consistently producing the most useful policy facts.
Examples of improvement but still partial:
- JetBlue NYC -> LAX
- Emirates NYC -> LAX
- Lufthansa MUC -> DEL business
- Current issue:
  - retrieval does not fully fail
  - but it still often gives “here is what we know, but exact checked-bag detail is missing”

7. Some answers are too conservative because the retrieved chunks do not expose exact fee tables or baggage facts.
Examples:
- JetBlue
- Turkish
- some Lufthansa and BA cases
- Current issue:
  - answer quality is bounded by what is actually surfaced from retrieved chunks
  - retrieval should do a better job of surfacing fact-bearing chunks and suppressing generic text

8. We still have possible ranking/noise issues inside linked policy retrieval.
Example:
- hub pages can still surface less useful sections instead of the most relevant baggage fact sections
- we need better section/fact ranking for:
  - carry_on
  - first_checked_bag
  - second_checked_bag
  - additional_policy

9. Airline normalization is improved but still needs to be treated as a first-class retrieval constraint.
Examples:
- JetBlue vs JetBlue Airways
- Emirates vs Emirates Airlines
- Current issue:
  - canonical airline matching exists now, but retrieval should be audited to ensure every relevant stage uses canonical airline consistently

10. Retrieval quality is still heavily dependent on corpus quality.
Examples:
- some airline pages are generic, blocked, or only partially useful
- even when retrieval works correctly, answer quality remains partial because fact extraction is weak or source content is shallow

What I want you to do:
1. Audit the current baggage retrieval flow end-to-end.
2. Identify where quality is lost:
   - row selection
   - facet inference
   - linked policy stage selection
   - policy_fact extraction quality
   - generic section fallback ranking
   - airline canonical matching
   - route/cabin/brand interpretation
3. Propose and implement retrieval-focused improvements.
4. If minimal indexing metadata changes are required to improve retrieval, make them too.
5. Do not redesign the whole service. Improve the current architecture.

Expected outputs:
- A concrete diagnosis of the current retrieval gaps
- Code changes
- Tests covering the regressions
- Re-run examples for the problem cases above
- A short evaluation summary showing what improved

Success criteria:
- Fewer partial baggage answers
- Better grounding for checked-bag details
- Better fare/brand awareness where evidence exists
- Better section/fact selection from hub pages
- Fewer generic or weak policy citations
