Fix the Flight Agent's usage of `getGeneratedContractsContext`.

The tool has two distinct responsibilities and the agent must not mix them:

### `mode: read`

Use when the agent needs to inspect existing generated flight options, for example:

* show available options;
* compare flights;
* find cheapest/fastest;
* understand how many contracts exist;
* answer questions about existing results.

`read` should inspect the available contracts **with their option/index references** so the agent knows which result is Option 1, Option 2, etc.

It must NOT select/change visibility while reading.

### `mode: select`

Use only when the user explicitly asks to display/select specific option numbers, e.g.:

* `"show option 4"`
* `"show 2 and 5"`

Then pass the required array of indexes and update visibility accordingly.

### Problem to Fix

Currently the agent sometimes:

* uses `read` but loses/misses the option indexes;
* uses `select` when it only needs to inspect results;
* reads only one indexed option when it actually needs all available contracts;
* cannot correctly map the contract back to the user's option number.

Strengthen the prompt/tool contract so:

`Need information/comparison → read all relevant contracts + preserve indexes`

`User explicitly selects option(s) → select with indexes`

Do not use `select` merely to inspect context.

Also inspect the tool response structure and ensure `read` returns enough information for the model to reliably map every contract to its option/index.

Keep the fix minimal and do not change unrelated Flight Agent behavior.

Add tests for:

* `show all options`
* `which is cheapest?`
* `compare option 2 and 4`
* `tell me about option 3`
* `show option 3`
* `show 2 and 5`
* `how many options do I have?`

For each case verify both the selected `mode` and indexes sent/returned.
