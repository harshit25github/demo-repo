We need to research **real-time image and icon hydration during Manager V2 response streaming**.

Currently, our backend hydrates locations only after the entire text response is complete. This causes users to see raw text for 1–2 seconds before images and icons appear.

I've shared a real **Mindtrip.ai SSE streaming trace**. Thoroughly analyze it and compare it with our implementation.

## Key Observation

Mindtrip streams both text and place metadata during generation.

Example from the trace (simplified):

```json
{
  "status": "in-progress",
  "data": [
    {
      "type": "text",
      "text": "Gardens by the Bay"
    },
    {
      "type": "place",
      "start": 258,
      "end": 276,
      "place": {
        "name": "Gardens by the Bay",
        "entity_ref": "at-UVT1vZlZ",
        "photos": ["..."]
      }
    }
  ]
}
```

The important observation is that **place metadata is emitted while text is streaming, rather than waiting for `done`**.

We don't know Mindtrip's internal architecture, but we can learn from this event contract.

## Explore Possible Solutions

**1. Progressive hydration using existing Trip Planner context (Preferred)**

- Can we obtain structured place references from Trip Planner before or during Manager text generation?
- Can we identify complete location mentions as text chunks arrive?
- Can we emit a lightweight place metadata event immediately?
- Can we resolve images asynchronously using our existing **Inventory API**, without blocking text streaming?
- Can the client attach icons immediately and update image previews independently when available?

**2. Semantic location references**

Explore lightweight markers or Markdown place references generated by the Manager, which the backend can recognize during streaming.

Evaluate whether stable place IDs and text offsets would be more reliable than location-name matching.

Ensure partial Markdown and chunk boundaries are handled correctly without exposing raw markers to users.

**3. Structured streaming events**

Investigate whether we should introduce a lightweight event such as:

```json
{
  "type": "place",
  "placeId": "place-123",
  "start": 258,
  "end": 276,
  "icon": "attraction",
  "imageUrl": "..."
}
```

The icon and image fields should become available independently when possible. Keep events small; avoid sending full place records or large photo arrays.

## Important Considerations

- Inspect the actual Manager, Trip Planner, hydration service, Inventory API, and SSE pipeline.
- Support places split across multiple text chunks.
- Handle repeated places, aliases, Unicode offsets, caching, missing images, and asynchronous responses arriving out of order.
- Avoid duplicate image requests and unnecessary LLM calls.
- Preserve smooth streaming without text flickering or replacing the entire response.
- Handle cancellation, retries, and failed hydration gracefully.
- **Manager V2 only. Gateway V1 must remain unchanged.**
